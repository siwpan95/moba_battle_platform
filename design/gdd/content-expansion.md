## 0. 执行摘要（TL;DR）

**本轮的核心结论是：当前不应先做"内容扩充"，应先做"内容修复"。**

实测发现一个 README 未披露、且会直接击穿平衡体系的结构性缺陷：

> **1659 名英雄中有 707 名（42.6%）只有 1 个技能**，而战斗引擎固定消费 4 个技能位
> （`core/simulator.py:314` → `available = [i for i in range(4)]`）。
> 这些英雄有 3 个空技能位，实测 **L9 平均胜率仅 18.3%**，对上完整英雄 **胜率 1.3%**。

同时，**7553 条技能中有 3024 条（40.0%）永远不会被引擎读取**——378 名英雄的技能表是
「6 条模板技能 × 重复 2 遍 = 12 条」，索引 ≥4 的部分是死数据。

因此 README 宣称的「92% / 75% / 63% 完整度」是**按声明条目统计的分母失真值**；按
**引擎可达的 4 技能位预算（1659 × 4 = 6636）** 重算，真实完整度为
**59.6% / 40.0% / 27.3%**。

**内容完整度已经成为当前版本唯一的主导策略变量（dominant strategy）**——玩家选谁赢，
取决于这张卡的数据填得全不全，而不是英雄设计。在此基础上新增 IP 只会等比放大失衡。

**建议路线：Wave 0 修复（P0）→ Wave 1 真实技能升级（P1）→ Wave 2 新增 IP（P2）**，
详见 §2。

### 1.6 根因：源技能文件覆盖缺口

`tools/card_generator.py:196` 按 `game_id` 从 `data/skills/<game_id>.json` 加载真实技能；
缺失时回落 `_templates.json` 角色模板。实测源文件条目数：

| IP | 卡数 | `data/skills/<ip>.json` 条目 | **缺口** |
|---|---|---|---|
| league_of_legends | 172 | 50 | **122** |
| smite | 130 | 12 | **118** |
| mobile_legends_bang_bang | 132 | 20 | **112** |
| dota2 | 126 | 15 | **111** |
| arena_of_valor | 115 | 10 | **105** |
| yinghunzhiren | 112 | 10 | **102** |
| honor_of_kings | 116 | 32 | **84** |
| onmyoji_arena | 83 | 10 | **73** |

> （596 源条目 → 574 张真实卡，命中率 96%）。补 1063 条源数据即可把真实覆盖推到 100%。

### 1.7 effects 维度盘点

`core/mechanics.categorize_effect` 用 20 张别名表归一（ADR-003），未识别归为
`flavor`（**仅记日志、不生效**）。

| 指标 | 全量 | **引擎可达** |
|---|---|---|
| effect 实例数 | 5700 | 2676 |
| **flavor 空转率** | 11.5% | **17.8%（475 条）** |

**可达 flavor Top 未映射类型**（修复 ROI 排序）：

| 未识别 `type` | 出现次数 | 建议动作 |
|---|---|---|
| `None`（缺 type 字段） | **352** | 数据修复：补 type |
| `'force'` | **164** | 映射到 `control`（击退/强制位移） |
| `'confuse'` | **100** | 映射到 `control` |
| `'位移'` | 19 | 映射到 `accel` 或新增 `dash` |
| `'闪避' '变身' '分身' '连击' '钩拽'` 等 | 各 1–5 | 长尾，归 flavor 可接受 |

> **仅修 `None` + `force` + `confuse` 三项即可覆盖 616/657 = 93.8% 的空转 effect。**

**另一处一致性缺陷**：`effect.type` 中英混用未统一——
`slow`(260) 与 `减速`(109)、`heal`(210) 与 `治疗`(74)、`buff`(269) 与 `强化`(170)、
`accel` 与 `加速`(207) 并存。别名表目前能吸收，但新增内容若继续混用会持续放大熵。

### 1.8 经济系统盘点

**实测结论：当前不存在任何经济系统。** 对 `core/`、`ui/` 全量检索
`装备 / item / rune / 符文 / gold / 金币 / inventory / shop` 无任何实现命中
（`catalog.py` / `registry.py` 的 `item` 为 dict 遍历变量，非游戏道具）。

战斗为「纯英雄 vs 英雄、无资源循环、无成长决策」。等级（1–18）是唯一的强度旋钮，
通过 `active_damage_scale = 1.0 + (avg_level−1) × 0.20` 生效。

## 2. 扩充范围与优先级

### 2.1 排序原则

> **护栏优先于产能。** 在胜率 σ = 33.3pp 的地基上新增英雄，等于把失衡按比例复制。
> 每一波扩充都必须先让上一波通过 §4 验收门。

范围分层采用 **MVP / 目标 / 愿景** 三档，对应 Wave 0 / 1 / 2。

### 2.2 Wave 0 — 残卡修复（P0，阻塞项，非"扩充"）

**目标**：消灭 T3_stub 与死数据，让 1659 名英雄全部具备 4 个可用技能位。

| 子项 | 范围 | 量 | 理由 |
|---|---|---|---|
| 0-A | 707 名残卡补齐至 4 槽（模板填充即可） | 2107 个空槽 | 直接消除 18.3% 胜率沙包 |
| 0-B | 378 名 12 技能卡裁剪至 4 条（去重复段） | 删 3024 条死数据 | 数据瘦身 40%，消除 key 语义错乱 |
| 0-C | 575 条零骰技能补 `dice_count` | 575 条 | 消除"打 0 伤害"的技能位 |
| 0-D | 模板 CD 重标定至引擎节奏 `[0,1,2,4]` 邻域 | 378 卡 × 4 槽 | 修 T4 的 4.73 平均 CD 缺陷 |
| 0-E | effects 别名补映射 `force`/`confuse` + 补 `None` type | 616 条 | 空转率 17.8% → ≤2% |

**Wave 0 后预期**：真实覆盖仍是 574（不变），但 **T3 归零**，胜率 σ 预期从 33.3pp
降至 15–20pp 区间。**这是后续所有扩充的地基。**

> ⚠️ 0-B / 0-D / 0-E 涉及改动 `data/` 与 `core/mechanics.py` 别名表，
> **超出本文档的只读授权范围**，需主理人另行派工给程基岩（工程）执行，
> 并由严守真（测试）回归。本 GDD 只定义目标与验收标准。

### 2.3 Wave 1 — 真实技能覆盖升级（P1，本轮主推）

**目标：真实技能覆盖 574（34.6%）→ 1100–1200（66–72%）。**

做法是补 `data/skills/<game_id>.json` 源条目（§1.6 已证明管线自动生效，无需改代码）。

**优先级排序原则**（按 `缺口 × IP 知名度 × 数据可得性` 加权）：

| 批次 | IP | 补源条目 | 理由 |
|---|---|---|---|
| **1-A** | league_of_legends | +122 | 缺口最大、认知度最高、公开资料最全 |
| **1-A** | honor_of_kings | +84 | 中文用户第一认知；已有 32 条可复用风格 |
| **1-A** | dota2 | +111 | 技能机制文档化程度极高，映射 D&D 最省力 |
| **1-B** | mobile_legends_bang_bang | +112 | 东南亚第一 MOBA，缺口大 |
| **1-B** | smite | +118 | 神话题材，**技能可用公有领域神话重述**，合规最优 |
| **1-B** | arena_of_valor | +105 | 与 HoK 英雄高度重合，可批量复用 |
| **1-C** | yinghunzhiren / onmyoji_arena / heroes_of_the_storm | +247 | 中量缺口 |
| **1-D** | pokemon_unite / marvel_super_war / vainglory | +164 | 缺口小；**vainglory 真实覆盖 0%，优先级可提前** |

**建议本轮承诺范围：1-A + 1-B（+652 条源技能，真实覆盖 → 约 1226 名 / 73.9%）**，
1-C/1-D 列为拉伸目标。

**替代方案（供拍板）**：
- **方案 A（推荐）**：1-A + 1-B，覆盖 → ~74%。工作量大但一次性解决大盘 IP 观感。
- **方案 B（保守）**：仅 1-A（+317），覆盖 → 53.7%。风险低，可先验证质量门。
- **方案 C（激进）**：1-A~1-D 全量（+1063），覆盖 → 100%。需评估数据采集人力。

> 我的取舍建议：**先跑方案 B 作为 1 个批次的质量门试点**，通过后直接推进到方案 A/C。
> 理由是 §4 的验收标准尚未在真实批次上校准过，一次性投 1063 条的返工风险不可控。

### 2.4 Wave 2 — 新增 IP / 英雄（P2）

**先说结论：本轮不建议新增商业 IP。** 理由有三：

1. **12 个大盘 MOBA IP 的花名册已基本饱和**——LoL 172、Dota2 126、HoK 116 已接近
   各自真实英雄总数，"新增英雄"在既有 IP 内空间很小。
2. **新增商业 IP 会线性放大 §5 的版权敞口**，而当前 24 IP 已有合规欠账未清。
3. **在 σ=33.3pp 未收敛前新增内容，等于把失衡复制到新 IP。**

**若要扩充，建议走"公有领域"路线**，目标 **+120～200 名英雄**：

| 来源 | 建议英雄数 | 理由 |
|---|---|---|

而非先定数字。以 Wave 1 单人产能校准后再锁定终值。下限 120 是形成"新阵营"体感的最小量，
上限 200 是不稀释既有 IP 辨识度的上界（占总盘 ≤11%）。

mage 372 / fighter 367 / tank 260 / marksman 246 / assassin 220 / support 194

理由是实现成本高、覆盖面 <0.1%，属于**支柱漂移**风险。

### 2.6 经济系统扩充（装备 / 符文 / 资源）— **建议本轮不做**

**结论：CONCERNS → 推迟到下一周期。**

**反对理由（取舍说明）**：

1. **平衡面积爆炸**：当前 1659 英雄的胜率 σ 已 33.3pp。引入 N 件装备会把平衡组合数
   从 `1659²` 推到 `1659² × C(N,k)`。在地基未修好前引入，**必然不可验证**。
2. **缺少经济循环载体**：1v1 单场对战无金币获取回合、无补刀、无防御塔，
   装备系统缺少"资源产出侧"，只能退化为**开局选 build**——那本质是"第二套属性面板"，
   不是经济系统。
3. **UX 载荷**：tkinter 桌面 UI 需新增商店/背包/符文页三个界面，
   属于林绘澄 + UX 的大改，超出"内容扩充"周期定义。
4. **与 D&D 5e 模型的耦合风险**：装备若给 flat AC / ATK 加成，会直接改变
   `1 − AC×0.005` 的减伤斜率，**等价于偷偷改了 DAMAGE_SCALE**，违反 §3 护栏。

**若用户坚持要做，最小可行替代方案（MVP，供拍板）**：

> **「D&D 装备词条」轻量版**：开局为每名英雄挂 **1 件**固定词条装备（不可选、按 role 派发），
> 词条只允许从**已有 effect 类别**中取值（如 `shield 10%` / `lifesteal 5%`），
> 不新增属性维度、不新增 UI 页（只在英雄卡详情多一行）。
> 这样平衡面积从 `C(N,k)` 降为 `6`（每 role 一件），可被 §4 验收门覆盖。

## 3. 与 D&D 5e 模型的对齐规则与平衡护栏

### 3.1 不可变量（Frozen Constants）

**本轮扩充期间，以下常量一律冻结，任何内容改动不得以"调这个数"来解决平衡问题：**

| 常量 | 值 | 位置 |
|---|---|---|
| `DAMAGE_SCALE` | **0.35** | `core/balance.py:12` |
| `HP_SCALE` | **10** | `core/balance.py:11` |
| `DND_DAMAGE_SCALE` | **5.5** | `core/simulator.py:18` |
| 物理减伤 | `1 − AC×0.005`，保底 30% | `core/engine.py` |
| 法术减伤 | `1 − WIS豁免×0.03`，保底 30% | `core/engine.py` |
| 引擎技能位数 | **4**（`range(4)`） | `core/simulator.py:314` |
| 默认槽冷却 | `[0, 1, 2, 4]` | `core/simulator.py:53` |
| 等级缩放 | `1.0 + (avg_lv−1)×0.20` | `core/simulator.py:66` |

**净伤害系数**（内容设计时的换算基准）：

```
final = raw_dice × mitigation × crit × DAMAGE_SCALE(0.35) × active_damage_scale(lv) × DND_DAMAGE_SCALE(5.5)

净常量 K = 0.35 × 5.5 = 1.925
L1  有效系数 = 1.925 × 1.00 = 1.925
L9  有效系数 = 1.925 × 2.60 = 5.005
L18 有效系数 = 1.925 × 4.40 = 8.470
```

> **护栏 G-1**：若某批新内容需要调 `DAMAGE_SCALE` 才能平衡，
> 判定为**该批内容设计失败**，退回重做，而非调旋钮。
> 理由：`DAMAGE_SCALE` 是全局旋钮，为局部内容调它会污染全部 1659 名英雄。

### 3.2 骰值预算规则（核心对齐规则）

**每名英雄在 4 技能位预算内的骰期望总和必须落入配额带。**

骰期望定义：`E = Σ_{i=0..3} dice_count_i × (dice_size_i + 1) / 2`

| 参数 | 值 | 推导 |
|---|---|---|
| 基准中心 | **29.4** | T1_real 实测均值（§1.9-D），已被验证可用 |
| **允许带宽** | **24.0 – 34.0** | 中心 ±17%，覆盖 T1 实测四分位 |
| 硬上限 | 36.0 | T4_tpl 均值 33.4 已偏高，不得再放宽 |
| 硬下限 | 22.0 | 低于此值复现 T3 沙包体质 |

**按 role 的带内偏置**（防止同质化，同时不越界）：

| role | 目标 E | 说明 |
|---|---|---|
| assassin | 32–34 | 高爆发，低 HP 补偿 |
| mage | 30–33 | AOE + 豁免减半，实际到手打折 |
| marksman | 29–32 | 持续输出 |
| fighter | 27–30 | 均衡 |
| tank | 24–27 | 低输出，由 HP/AC 补偿 |
| support | 24–27 | 低输出，由 heal/shield 补偿 |

### 3.3 冷却预算规则

针对 §1.9-D 暴露的 T4 高 CD 缺陷：

> **护栏 G-2**：单英雄 4 槽的**平均 CD 必须 ≤ 3.0**，**最大 CD ≤ 5**。
> 槽 0 的 CD **必须为 0**（保证任何回合都有可用技能，杜绝"无技能可放"退化）。

推导依据：引擎默认 `[0,1,2,4]` 平均 = 1.75；T1_real 实测 2.88 表现健康；
T4_tpl 4.73 表现失败。取 3.0 为上界。

### 3.4 属性与 HP 对齐规则

| 规则 | 约束 | 理由 |

| G-6 | `hit_die` 必须与 role 一致（tank=12/fighter=10/mage=6…） | 与 `tools/hero_calculator.py` 一致性 |

## 附录 A — 复核方法说明

本文档全部数字可复现，方法如下（均为只读）：

1. **卡与技能盘点**：遍历 `data/character_cards/*/*.json`，统计 `skills[]` 长度分布、
   `damage/effects/saving_throw` 字段存在性；区分全量与 `skills[0:4]` 两个口径。
2. **可达性判据**：读 `core/simulator.py` 的 `_choose_skill`（`range(4)`）与
   `_get_skill`（`idx < len(skills)`）确认引擎只消费前 4 条。
3. **T1–T4 分层**：以 `data/skills/_templates.json` 递归抽取的模板名集合 +
   角色前缀正则 + 泛称正则作为"模板名"判据。
4. **effects 归一**：直接 `import core.mechanics.categorize_effect` 对全部 effect 实例
   分类，统计 `flavor` 占比与未识别 `type` 频次。
5. **平衡基线**：`import core.simulator.BattleSimulator`，固定 `random.Random(20260805)`，
   60 回合上限，按 §4.3 采样协议跑 A/B/C 三组实验。
6. **源覆盖缺口**：对比 `data/skills/<game_id>.json` 的有效英雄条目数与
   `data/character_cards/<game_id>/` 的卡数。
