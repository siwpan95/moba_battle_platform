## 1. 1078 张缺陷卡再生（700 list[1] + 378 list[12]）

### 判定：CONCERNS

### 1.1 模板 CD 校准——**当前状态：未完成，P0 阻塞 Phase B**

我的 GDD §1.9-D 实测暴露了模板技能的致命缺陷：

> T4 模板平均 CD = **4.73**，最大 = **6.83**，而引擎默认 `[0,1,2,4]` 平均 = 1.75，
> T1_real 实测 2.88。T4 骰期望最高（33.4）却打不过 T1（29.4），**输在 CD 脱节**。

GDD §2.2 子项 **0-D** 明确将此列为 Wave 0 P0 交付项：
> 模板 CD 重标定至引擎节奏 `[0,1,2,4]` 邻域 | 378 卡 × 4 槽 | 修 T4 的 4.73 平均 CD 缺陷

GDD §3.3 护栏 G-2 定义了硬性规则：
- 单英雄 4 槽**平均 CD ≤ 3.0**
- **最大 CD ≤ 5**
- **槽 0 CD == 0**（保证任何回合都有可用技能）

**程基岩的 dry-run 报告对 CD 值只字未提。** 管线就绪评估也只涉及 `cooldown` 字段的结构存在性（字段白名单透传），未涉及 CD 数值的校准。这意味着：

- 700 张残卡 regener 后将获得 4 个模板技能——但 CD 仍是旧的 4.73 节奏
- 378 张死数据卡裁剪为 4 条——但保留的 4 条 CD 仍是旧的 4.73 节奏
- **这些卡会从"1 技沙包（胜率 18.3%）"变成"4 技假完整（胜率约 65%）"——仍然打不过 T1 真实卡（分层对位 88.1% → 可能仍有 70%+ 劣势）**

**这不是拒绝修复的理由，而是修复不完整的警告。** Wave 0 的目标是让胜率 σ 从 33.3pp 降到 ≤20pp（GDD §2.2）。如果只修槽位数不修 CD，σ 降幅会远低于预期，Gate C-2（≤20pp）可能失败。

**条件 C1**：Phase B 执行前，必须完成 `_templates.json` 中全部 6 role × 多模板的 CD 校准，逐槽满足 G-2（槽 0 CD==0，平均 ≤3.0，最大 ≤5）。建议由程基岩实现 `tools/recalibrate_template_cd.py`，批量修改模板 CD 字段，并纳入 CI 门禁。

### 1.2 模板技能同质化——"伪完整"风险（GDD R-1 实锤）

GDD §5 风险 **R-1** 预见了这个问题：

> 若沿用现有模板化思路，会批量产出 T4 级"伪真实"内容——名字真实但机制同质，
> 重演 T4 的 88.1% 败率问题。

程基岩在管线就绪评估 ADR-005（`:659`）中提出的方案是 `_load_templates()[role][:4]`——
取前 4 个模板技能。**这恰好是 R-1 最担心的场景：**

- 同一个 role 的所有模板填充英雄获得**完全相同的 4 个技能**
- 以 `fighter` 为例：78 张 Dota + 79 张 SMITE + …… = 数百张 fighter 卡技能完全一致
- 它们唯一的区别是 `hero.name` 和 `stats`（由 D&D 车卡随机生成）
- **这不是 1078 张独立英雄，而是 6 个 role × 1 套模板 = 6 种"皮肤"**

**条件 C2**：模板回退路径必须采用**基于英雄名的确定性多样化选择**，而非固定 `[:4]`。具体方案：

```
方案（推荐）：对每个英雄，用 `hash(hero_name) % len(templates)` 作为起始偏移，
取 `templates[offset:offset+4]`（循环 wrap）。这样：
- 同 role 不同英雄获得不同的 4 技能组合（多样化）
- 同英雄每次生成结果一致（幂等，满足 ADR-005 幂等要求）
- 每个英雄仍然 4 槽填满（契约合规）
```

替代方案（次选）：每个 role 提供 ≥12 个模板技能（当前仅 6 个），`random.sample(flat, 4)` +
固定 seed = `hash(hero_name)`。当前模板池过小（6 选 4 = 15 种组合，远不够 700 英雄分）。

### 1.3 `approx: true` 标记——区分"真技能"与"模板占位"

管线就绪评估 ADR-005（`:685`）明确要求：

> 正确做法是让回退**产出合约内的 4 技能占位**，并用 `approx: true` 标记待人工精修。

但 dry-run 报告未提及 `approx: true` 标记策略。当前数据中 `approx` 字段已存在 612 处
（管线评估 §4.1），但 `_to_skill_dict` 白名单会静默丢弃它（管线评估 §4.2）——
这是一个鸡生蛋蛋生鸡的问题：标记了也会被丢掉。

**程基岩的 ADR-005 决策 4 已将 `_to_skill_dict` 改为透传模式**（管线评估 §7 决策 4），
`approx` 字段将得以保留。在此基础上：

**条件 C3**：Phase B regener 的所有 1078 张卡，其全部 4 个技能必须标记 `"approx": true`。
这与 GDD Gate A-2（"非模板泛称"）形成双重保障——前者从结构上标记，后者从命名上校验。
当 Wave 1 补入真实技能数据后，`approx: true` 技能被替换时自动翻为 `false` 或移除该字段。

### 1.4 建议：先试点再全量

GDD §5 R-1 缓解措施第 ③ 条：
> 先跑方案 B（317 条）校准，再放量。

**条件 C4**：Phase B 不要一次性 regener 全部 1078 张。建议分 3 个子批次：

| 子批次 | IP | 缺陷卡数 | 理由 |
|--------|-----|---------|------|
| B-1（试点） | vainglory（仅 25 list[1] + 22 list[12] = 47） | 47 | 最小批，先验证 CD 校准效果 + 同质化程度 |
| B-2 | 选 2–3 个中型 IP（如 pokemon_unite 44+15=59、marvel_super_war 45+13=58） | ~120 | 扩大验证，跑 Gate C 平衡门 |
| B-3 | 剩余全部 | ~911 | 试点通过后再放量 |

每批次完成后跑 §4 Gate C 平衡门（L9, 40 局/英雄），绿了才进下一批。
这与我 GDD §5 R-4 的灰度推进策略一致。

## 2. 574 张完整卡仅 card_id 变

### 判定：PASS

### 2.1 card_id 格式变更：`LOL-1400` → `league_of_legends:亚索`

从内容设计角度，这个变更是**改进而非伤害**：

| 维度 | 旧格式 `LOL-1400` | 新格式 `league_of_legends:亚索` | 评价 |
|------|-------------------|-------------------------------|------|
| IP 可追溯 | 需查前缀映射表（`LOL` = ?） | game_id 自描述 | ✅ 更好 |
| 英雄可辨识 | 序号 1400，需反查 | 英雄名直接可读 | ✅ 更好 |
| 阵营/关系查询 | 通过 card_id 前缀过滤 | 通过 `game_id:` 前缀过滤 | ✅ 等价 |
| 跨工具引用 | 短 ASCII，脚本友好 | 含中文和冒号，需引号处理 | ⚠️ 需注意 |
| 幂等性 | 依赖全量生成序号，局部生成会变 | `game_id:hero_slug` 物理路径同构 | ✅ 更好 |

**关于阵营/关系/来源追溯能力**——新格式 `game_id:hero_slug` 比旧格式**更有利于内容设计**：
- 旧格式需要维护一份 `LOL→league_of_legends` 映射表才能做 IP 聚合
- 新格式的 `game_id` 前缀天然可做 `split(":")[0]` 分组
- 中文英雄名让设计师无需翻查即可识别这是谁

唯一的小瑕疵：中文冒号与英文冒号在 Windows 文件名中均合法，但在 URL 编码场景需注意。
`legacy_card_id` 保留过渡期，已充分缓解破坏性。

**结论：PASS。无需额外条件。**

### 2.2 Skills 内容完全不动——从内容一致性角度

574 张完整卡（T1_real + T2_partial）的 skills 内容与再生后**完全一致**（dry-run 报告 §2.5）。
这验证了管线就绪评估 §3.1 的结论：这些卡走技能 DB 精确命中路径，不落模板回退，内容稳定。

从内容一致性角度，**这是最安全的做法**：
- 这些卡是经过 GDD §1.4 分层验证的 T1/T2 真实技能卡
- 它们构成了平台的"内容黄金标准"——任何 regener 都不应改动它们
- 只改 card_id 不动 skills = 零内容风险

**结论：PASS。保持不动是正确的。**

## 3. Vainglory 7 张 list[3] 卡（A/B/U 键位，真实技能数据）

### 判定：PASS（附条件——文档化例外）

### 3.1 事实核查

GDD §1.5 标记 Vainglory 真实覆盖为 **0%**（T1=0, T2=0）。程基岩发现其中 7 张有真实技能数据：
键位使用 A/B/U（Vainglory 原生格式），而非 Q/W/E/R。内容不变。

**我的 GDD 在此处有误**：那 7 张卡应归为 T2_partial（3 槽真实技能 + 1 槽空缺），
而非全部归入 T3。修正后 Vainglory 真实覆盖 = 7/54 = 13.0%。这不影响 GDD 的核心结论
（Vainglory 仍是真实覆盖最低的 IP 之一），但需要做一条勘误。

### 3.2 是否应补齐为 4 槽？

**不同意补齐。理由：**

1. **忠实还原优先于机械合规**：A/B/U 是 Vainglory 游戏的真实键位体系。强塞第 4 个模板技能（标记为 "R"）会破坏这种 IP 真实性。内容设计的设计支柱之一是"MOBA→D&D 转译的忠实度"——3 槽 Vainglory 本身就是忠实转译。

2. **引擎已能优雅降级**：`core/simulator.py` 的 `_get_skill` 对 `idx >= len(skills)` 返回 `None`，`_choose_skill`（`range(4)`）在槽 3 为空时自动回退槽 0（平 A）。不会崩溃。

3. **Gate 例外比数据造假好**：给这 7 张卡塞一个模板技能凑成 4 槽，本质是**数据造假**。这些卡在 Vainglory 技能 DB 中本来就只有 3 条数据，硬补第 4 条等于引入了不可信内容。

### 3.3 条件

**条件 C5**：在 GDD 和 Gate A-1 文档中为 Vainglory 3 槽卡建立**正式例外条款**：
- Gate A-1 的 `len(skills) == 4` 改为 `len(skills) >= 3`，并将 Vainglory 的 3 槽标记为 `intentional_3slot: true`
- 这 7 张卡的 `key` 保持 `A/B/U`（不做 Q/W/E/R 转换）
- 在英雄卡元数据中增加 `"skill_slots": 3` 字段，与标准 `4` 区分

**这不构成放行阻塞**——Phase A/B 执行时这 7 张卡只改 card_id、不动 skills，安全。

## 4. 分阶段执行方案审阅

### 判定：PASS（同意 Phase A → Phase B 分法，附条件清单）

### 4.1 同意 Phase A（全量 card_id 迁移）先行

理由：
- card_id 迁移是纯标识变更，不影响战斗内容
- 574 张完整卡 + 7 张 Vainglory 3 槽卡 = 581 张零内容风险
- 1078 张缺陷卡在 Phase A 也只改 card_id，不动 skills——它们保持缺陷状态，但获得了新 ID
- Phase A 完成后，全库 card_id 格式统一，ADR-005 幂等保证生效
- 是一次干净的"格式归一化"，为 Phase B 建立稳定的标识基础

**Phase A 可立即执行，无需额外条件。** 唯一建议：执行后跑一轮 Gate C 基线快照（新旧 card_id 下胜率应完全一致），作为 Phase B 的前后对比基准。

### 4.2 同意 Phase B 仅 regener 缺陷卡（不碰 574 完整卡）

理由：
- 574 张完整卡是 T1/T2 真实技能卡，内容黄金标准，不应承担任何 regener 风险
- dry-run 证实这 574 张在 regener 路径下内容不变（§2.5），但仍建议不要无谓重写磁盘
- 全量 regener（包括完整卡）会引入不必要的磁盘变更噪音，增加 diff review 成本
- **"同一次生成批次一致性"的顾虑不成立**——这 574 张走的是技能 DB 精确命中路径，不经过模板回退。它们的内容由 `data/skills/<game_id>.json` 锁定，与生成批次无关

### 4.3 Phase B 执行前置条件清单（全部必须满足）

| # | 条件 | 来源 | 阻塞级别 |
|---|------|------|----------|
| **C1** | `_templates.json` 全部模板技能 CD 校准至 G-2 护栏（槽 0 CD==0，平均 ≤3.0，最大 ≤5） | GDD §2.2 0-D / §3.3 | **P0 — 不放行则 Phase B 产出有平衡缺陷的卡** |
| **C2** | 模板回退路径采用英雄名哈希确定性多样化选择（非固定 `[:4]`） | GDD §5 R-1 | **P0 — 不放行则 1078 张卡仅 6 种技能组合** |
| **C3** | 所有再生缺陷卡的 4 技能均标记 `"approx": true` | 管线评估 ADR-005 :685 | **P0 — 不放行则无法区分真技能和模板占位** |
| **C4** | Phase B 分 3 个子批次灰度推进（47 → ~120 → ~911），每批跑 Gate C | GDD §5 R-4 | **P1 — 不放行可执行但风险不可控** |
| **C5** | Vainglory 7 张 3 槽卡建立 Gate A-1 正式例外条款 | 本审阅 §3 | **P1 — 不阻塞 Phase A/B，但需在 Gate 更新前完成** |
| **C6** | Phase B 试点批次（B-1）选 vainglory 47 张，先验证 CD 校准效果 | 本审阅 §1.4 | P1 — 建议 |
| **C7** | 补充 `approx` 字段到 `core/schema.py` 白名单（如 C-4 修复未涵盖） | 管线评估 BLOCKER-4 | P1 — 否则 `approx: true` 标记仍会被丢弃 |

### 4.4 明确：不推荐全量 regener（包括 574 完整卡）

全量 regener 会带来不必要的风险：
- 574 张完整卡的技能数据由 `data/skills/<game_id>.json` 锁定——regener 它们除了重写磁盘无任何收益
- 管线就绪评估 §4.3 提到的 `random.sample` 非确定性问题虽然对完整卡不适用（它们走技能 DB 精确命中），但**任何全量操作都增加了误触风险**
- 磁盘 diff 噪音会淹没真正需要 review 的 1078 张变更

**结论：Phase A + Phase B（仅缺陷卡）= 最优方案。程基岩的分阶段建议与我的内容风险管控策略一致。**

## 5. 补充发现

### 5.1 GDD 自身勘误

GDD §1.5 Vainglory 一行：

> | vainglory | 54 | 0 | 0 | 22 | **32** | **0.0%** |

应修正为：

> | vainglory | 54 | 0 | 7 | 22 | **25** | **13.0%** |

（7 张 A/B/U 3 槽卡为 T2_partial，非 T3_stub）

### 5.2 GDD 未覆盖的 `approx` 策略

我的 GDD 在设计时未涉及 `approx: true` 标记策略——这个字段当时已存在于数据中（612 处）但我未将其纳入设计框架。管线就绪评估 §7 ADR-005 将它定为"真技能 vs 模板占位"的判定标记，我完全同意并在此将其正式纳入 GDD 验收体系：

- Gate A-2 的"非模板泛称"判定加入辅助条件：`approx: true` 的技能即使名字不是泛称，也视为模板占位
- Wave 1 真技能替换时的验收标准新增：替换后移除对应技能的 `approx` 标记

### 5.3 程基岩的 `--all` 执行前建议

如果程基岩要执行 `--all`（而非分阶段），请确保以下已就位：

1. C1（CD 校准）——最重要的一条，没有商量的余地
2. C2（多样化选择）——否则生成的是 6 种皮肤，不是 1078 个英雄
3. C3（`approx: true`）——这是后续 Wave 1 真技能替换的唯一路标
4. dry-run 报告 §4.3 提到的"确定性选择取代 random.sample()"——程基岩自己已经在报告里建议了，请务必并入 C2 方案
