## 0. 执行摘要（TL;DR）

**Wave 1 的定位是"质量升级"：把已有 IP 的 1078 张 T4 模板卡升级为真技能卡，而非新增 IP。**

核心策略不变：**先跑方案 B（LoL + HoK + Dota2，共 317 条）作为质量门试点**，通过后直接推进到方案 A（+652 条，覆盖 6 个大盘 IP）。不推荐一次性全量 1078 条——数据采集产能和质量风险不可控。

**最关键的前置条件**：Wave 0-D（模板 CD/骰值标定）必须在 Wave 1 第一批数据合入前完成。当前 σ=25.8pp 与目标 ≤20pp 的差距主要来自模板技能 CD/骰值偏离配额带，而新增的源技能会自动继承正确的 CD——因此 Wave 0-D 和 Wave 1 第一批建议**并行推进**，合入前统一通过 Gate C。

**预期终点**：Wave 1 方案 A 完成后，真实覆盖从 23.1% → ~60%，σ 预期降至 12–15pp，T1 vs T4 对位胜率差距从 84.8% 大幅收窄。

## 1. Wave 1 定位：质量升级 vs 数量扩张

### 1.1 术语澄清

当前用户目标"扩大英雄池（IP数量 + 角色卡数量）"实际上是 **Wave 1 + Wave 2 的联合效果**，需要明确分工：

| 维度 | Wave 1（本方案） | Wave 2（后续） |
|---|---|---|
| **做什么** | 已有 IP 内，模板卡 → 真技能卡 | 新增公有领域 IP + 新英雄卡 |
| **英雄数变化** | 不变（1659→1659） | +120~200 |
| **IP 数变化** | 不变（24） | +3~5 |
| **玩家体感变化** | "同一个英雄终于有自己技能了" | "多了新阵营可选" |
| **对 σ 的影响** | 消除 T1/T4 分层，σ↓ | 轻微 ↑ 后通过验收门拉回 |
| **本质** | **质量升级（depth）** | **数量扩张（breadth）** |

> **一句话**：Wave 1 解决"1078 个英雄用通用模板技能打架"的体验问题；Wave 2 才是真正扩大池子。二者顺序不可互换——在模板卡还占 65% 时新增 IP，等于把"名字不同但技能雷同"的问题复制到新阵营。

### 1.2 Wave 1 完成定义（Definition of Done）

| 指标 | 当前 | Wave 1 完成 |
|---|---|---|
| 真实技能覆盖（T1+T2） | 574（34.6%） | ≥ 1100（≥ 66%） |
| T4 模板卡 | 1078 张 | ≤ 450 张 |
| 12 大盘 IP 源文件覆盖率 | 201/1264（15.9%） | ≥ 652/1264（≥ 51.6%） |
| 全池胜率 σ | 25.8pp | ≤ 15pp |
| T1 vs T4 对位胜率差距 | 84.8% | ≤ 65%（趋势性改善，不要求到 55%） |

## 2. 优先级排序（更新 GDD §2.3）

### 2.1 排序原则（修正版）

GDD §2.1 原始排序公式为 `缺口 × IP 知名度 × 数据可得性`。在 σ=25.8pp 的新现状下，**增加第四个因子：对 σ 收敛的边际贡献**。

| 因子 | 权重 | 说明 |
|---|---|---|
| 缺口大小 | 30% | 缺口越大，转化 T4→T1 的量越大 |
| 数据可得性 | 30% | Wiki 完善度、中英文资料量、技能机制文档化程度 |
| IP 知名度 | 20% | 玩家认知度 → 体感改善的放大效应 |
| σ 收敛贡献 | 20% | 该 IP 内 T4 英雄当前胜率方差——方差越大的 IP，真技能替换后 σ 下降越明显 |

### 2.3 GDD §2.3 建议的再评估

**GDD 原始建议**："先跑方案 B 作为 1 个批次的质量门试点（+317：LoL + HoK + Dota2），通过后直接推进方案 A。"

**当前评估：建议仍然成立，但需要微调。**

| 维度 | GDD 假设 | Wave 0 后实际 | 对建议的影响 |
|---|---|---|---|
| σ 基线 | 预期 Wave 0 后 15–20pp | **实际 25.8pp** | 方案 B 的 σ 改善预期需下调 3-5pp |
| T4 卡数 | 378（22.8%） | **1078（65.0%）** | 方案 B 覆盖比例从 ~84% 降为 ~29% |
| 模板 CD 标定 | 假设已完成 | **CD 合规率 79.4%** | Wave 0-D 必须与 Wave 1 并行 |
| 数据采集路径 | 未详述 | — | 本方案 §5 补全 |

**修正建议**：

1. **方案 B 拆分为 B1 + B2**（而非一笔大批次）：B1 = LoL（+134），B2 = HoK + Dota2（+198）。B1 跑通数据采集 → 审查 → 合入全流程，校准产能和验收门后再放量 B2。
2. **并行推进 Wave 0-D**（模板 CD/骰值标定），确保第一批真实技能合入前 σ 基底已降至 ≤20pp。
3. **方案 A 从 "1-A + 1-B 全部" 调整为 "1-A → 1-C"**：LoL + Dota2 + HoK + Smite + MLBB + AoV（6 个 IP，共 ~667 条），略多于原方案 A 的 652 但 IP 优先级重排后更合理。

|---|---|---|---|---|---|

| **1-A** | league_of_legends | +134 | 42.6% | ≤ 18pp | 3-5 天 |
| **1-B** | honor_of_kings + dota2 | +198 | 54.6% | ≤ 15pp | 4-6 天 |

> **承诺范围：1-A + 1-B + 1-C（共 667 条）**。1-D/1-E 列为拉伸目标，视产能和 σ 收敛速度决定是否推进。

### 3.2 每批次验收标准（自动化 Gate，由严守真执行）

每个批次合入前，必须通过以下全部 Gate：

#### Gate C（平衡性）— 每批采样协议

| 参数 | 值 |
|---|---|
| 等级 | L9 |
| 种子 | 固定 20260805 |
| 回合上限 | 60 |
| 采样英雄 | ≥ 120 名（覆盖本批新增 + 存量对照） |
| 每英雄对局 | 40 局 vs 全池随机 |
| 分层对位专项 | T1 vs T4：600 局；新增 T1 vs 存量 T1：600 局 |

| ID | 判据 | 阈值 | 备注 |
|---|---|---|---|
| C-2 | 全池胜率 σ | **本批前 ≤ 本批后**（不上升） | 每批递进目标见 §3.1 |
| C-5 | 极值英雄（<25% 或 >75%） | **≤ 本批前数量** | 只降不升 |
| C-6 | T1 vs T4 对位胜率差距 | **≤ 本批前 − 5pp** | 每批必须有趋势性改善 |
| C-7~C-12 | 战斗节奏全套 | 同 GDD §4.3 阈值 | 不得因内容扩充劣化 |
| C-13 | 骰期望落入配额带（24–34） | **≥ 95% 新增英雄** | 本批新增重点 |
| C-14 | CD 合规（avg≤3.0, s0=0） | **100% 新增英雄** | 硬门 |

#### Gate E（IP 合规）— 每批抽检

| ID | 判据 | 抽检率 |
|---|---|---|
| E-1 | 技能描述与官方 wiki 文本相似度 < 40% | 10%，≥ 5 条 |
| E-6 | 技能机制为 D&D 5e 再诠释（非官方数值搬运） | 10%，≥ 5 条 |

#### 每批通过条件

```
PASS   : 本批 Gate C + Gate E 所有项目达标 + Gate D 无退化
HOLD   : C-2/C-5/C-6 有改善但未达标 → 本批可暂存，不阻塞下一批数据采集，但不得合入
FAIL   : 任一 Gate D 退化或 Gate C-7~C-12 劣化 → 本批退回，暂停后续批次
```

### 3.3 具体批次说明

#### Wave 0-D（前置批次 — P0 阻塞项）

**不涉及新内容，仅校标已有数据。** 由程基岩执行：

1. 遍历 1078 张 T4 模板卡，验证 `len(skills)==4`、`skills[0].cooldown==0`
2. 重算骰期望 E，确保落入 24–34 配额带（当前 C-13 合规率仅 49.6%）
3. 修正 `_templates.json` 中不合理的 dice_count/dice_size 组合
4. 严守真跑 Gate C 全量回归，验证 σ ≤ 20pp

**放行条件**：σ ≤ 20pp 且 C-13 合规率 ≥ 90%、C-14 合规率 ≥ 95%。

#### 批次 1-A：league_of_legends（+134 条）

**为什么 LoL 第一批**：
- 缺口最大（134/1078=12.4%），单 IP 贡献最高
- 公开资料最全（League of Legends Wiki、社区 D&D 转换表完整）
- 已有 50 条源数据（含 盖伦/亚索/劫/阿狸 等标杆）可作风格基线
- 验证数据采集→审查→合入全流程，为后续批次校准产能

**预期效果**：
- T4 从 1078 → 944（↓12.4%）；T1 从 383 → 517
- σ 预期 25.8 → ~18pp（T1 占比提升 + T1 内部强度分布改善）
- T1 vs T4 预期 84.8% → ~75%

**特殊处理**：LoL 有 50 条源数据包含 12 条"死匹配"（源文件有但卡片名不匹配），需逐一核对是重命名还是数据作废。

#### 批次 1-B：honor_of_kings（+84）+ dota2（+114）= +198 条

**为什么这两个 IP 合并**：
- HoK 是中文用户第一认知，但缺口相对小（84）
- Dota2 技能机制文档化程度极高（Dota 2 Wiki + D&D 社区转换），可批量映射
- 两者合并达到 198 条，接近 1-A 的 134 条规模，保证每批有统计显著性

**预期效果**：
- 真实覆盖 → 54.6%，σ → ≤15pp
- 此时 T1 vs T4 的样本量足够大（~900 张 T1 vs ~600 张 T4），分层对位测试更有统计效力

#### 批次 1-C：smite + mobile_legends_bang_bang + arena_of_valor（+335 条）

**为什么 smite 优先级提升**：smite 的神话英雄技能可以**用公有领域神话重述**（§5.2 详述），合规风险最低。

**Arena_of_valor 特殊处理**：与 honor_of_kings 英雄高度重合（如 "亚瑟" = "亚瑟王"），可复用 HoK 的技能数据框架，加速采集。

#### 批次 1-D / 1-E（拉伸目标）

视前 3 批的产能数据和 σ 收敛曲线决定是否推进。若 1-C 完成后 σ 已 ≤ 12pp，1-D/1-E 的边际收益递减，可考虑直接跳 Wave 2。

## 4. 数据供给策略

### 4.1 核心约束

| 约束 | 说明 |
|---|---|
| **禁止 AI 虚构技能名** | 技能名必须来自 IP 真实技能，不可由 LLM 凭空编造 |
| **禁止逐字搬运官方描述** | Gate E-1：与 wiki 原文相似度 < 40% |
| **必须 D&D 5e 化** | 技能机制是"D&D 5e 诠释"，非官方数值搬运（Gate E-6） |
| **必须 CD 合规** | 源数据写入时即保证 `cooldown=[0,1,2,4]`、`key=["Q","W","E","R"]` |

### 4.2 推荐路径：半自动采集 + 人工审查

```
Phase 1: 爬取（半自动）         Phase 2: 映射（结构化）       Phase 3: 审查（人工）
┌──────────────────┐     ┌──────────────────────┐     ┌──────────────────┐
│ 公开 Wiki / DB    │ →   │ Hero → 4 Skill Names │ →   │ D&D 5e 数值填入   │ →   │ 人工质量审查     │
│ • League Wiki     │     │ Skill → Role 推断    │     │ dice_count/size  │     │ • IP 合规抽检   │
│ • Dota 2 Wiki     │     │ Skill → Type 推断    │     │ effects 设计     │     │ • 机制辨识度    │
│ • HoK 官网        │     │ (damage/CC/mobility) │     │ saving_throw     │     │ • CD/骰值验证   │
│ • Liquipedia      │     │                      │     │ cooldown 标定    │     │ • 风格一致性    │
└──────────────────┘     └──────────────────────┘     └──────────────────┘
```

### 4.3 Phase 1：爬取 — 技能名映射表

**输入**：角色卡已存在的英雄名（如 `丽桑卓`）

**输出**：`hero_name → [skill1_name, skill2_name, skill3_name, skill4_name]` 映射表

**可用数据源**：

| IP | 推荐数据源 | 语言 | 完备度 |
|---|---|---|---|
| league_of_legends | leagueoflegends.fandom.com / Data Dragon API | EN/ZH | ★★★★★ |
| dota2 | dota2.fandom.com / OpenDota API | EN/ZH | ★★★★★ |
| honor_of_kings | 王者荣耀官网 / pvp.qq.com | ZH | ★★★★ |
| smite | smite.fandom.com | EN | ★★★★ |
| mobile_legends_bang_bang | mobile-legends.fandom.com | EN | ★★★★ |
| arena_of_valor | aov.fandom.com | EN | ★★★ |
| heroes_of_the_storm | heroesofthestorm.fandom.com | EN | ★★★★ |
| 其余 IP | 各 fandom wiki | EN/ZH | ★★~★★★ |

**工具建议**：编写 `tools/scrape_skill_names.py`（只读脚本），输入 IP 名，输出 JSON 映射表。
该脚本不写入 `data/`，仅生成 `production/wave1_skill_maps/<ip>_names.json` 供 Phase 2 消费。

### 4.4 Phase 2：结构化映射 — 技能名 → D&D 5e 数据

这是工作量最大的阶段。每个技能需要填入约 15 个字段。

**分层映射策略**：

| 技能类型 | 推断方法 | D&D 5e 映射规则 | 示例 |
|---|---|---|---|
| **伤害技能**（最常见） | 技能名含"打击/射击/飞弹/斩/波"或 wiki 标签为 damage | `dice_count=[1,2]`，`dice_size=[6,8,10,12]` 按 slot 递增，`bonus_attr`=主属性 | 亚索 Q"斩钢闪"→ 1d8+DEX |
| **控制技能**（CC） | wiki 标签含 stun/slow/root/knockup | `dice_count=1`，低 dice_size，重点在 `effects[control/slow]` | 丽桑卓 W"冰霜之环"→ 1d6+INT + 2回合束缚 |
| **位移技能**（mobility） | wiki 标签含 dash/blink/leap | `dice_count=1`，`effects[dash]`，中等 dice_size | 伊泽瑞尔 E"奥术跃迁"→ 1d8+DEX + dash |
| **护盾/治疗**（defense） | wiki 标签含 shield/heal | `dice_count=0`，纯 `effects[shield/heal]` | 卡尔玛 E"鼓舞"→ shield 15% |
| **增益/减益**（buff/debuff） | wiki 标签含 buff/debuff | `dice_count=0~1`，`effects[buff/debuff]` | 努努 W"热血沸腾"→ buff ATK+3 |

**骰值配额自动校验**：每做完一个英雄，脚本自动计算 `E = Σ dice_count_i × (dice_size_i + 1) / 2`，检查是否落入 §3.2 配额带（24–34），不通过则标记人工重调。

**参考基线**：利用同 IP 已有源数据（如 LoL 的 50 条、HoK 的 32 条）作风格基线——新技能与同 role 已有技能的 dice_size 分布、effects 复杂度、saving_throw 覆盖率保持一致。

### 4.5 Phase 3：人工审查 — 两道关口

**关口 A — 机制审查**（文策渊 / 设计侧）：
- 抽查 10% 技能，验证"机制辨识度"——同一 IP 内不同英雄的技能 effects 不应高度同质化
- 验证骰期望分布符合 role 偏置（§3.2 的 6 档 role 目标）
- 检查跨英雄技能名是否唯一（杜绝"两个英雄都有叫 '火球术' 的技能"——template 名除外）

**关口 B — IP 合规审查**（用户 / 法务侧）：
- 抽检技能描述是否改写充分（与 wiki 原文相似度）
- 商业 IP 技能文本改写 vs 原始搬运的边界确认
- smite 神话英雄是否走公有领域路线

### 4.6 产能估计

基于 Phase 2 的复杂度：

| 指标 | 估计值 | 推导 |
|---|---|---|
| 单个技能 D&D 映射 | 2–5 分钟 | 取决于技能复杂度（纯伤害最快，CC+豁免最慢） |
| 单个英雄（4 技能） | 8–20 分钟 | Phase 2 纯手工 |
| 一个 IP（~100 英雄） | 13–33 小时 | 考虑熟练度提升 |
| 批次 1-A（LoL, 134） | **18–45 小时** | Phase 2 工作量 |
| 批次 1-A + 1-B（332） | **44–111 小时** | Phase 2 工作量 |

> **产能风险**：如果纯人工做 Phase 2，1-A + 1-B 需要 2–4 周（单人全职）。建议对 LoL/Dota2 优先开发半自动映射脚本（利用已有的 D&D 社区转换数据），可将产能提升 3–5×。

## 5. 与 Wave 2 的衔接

### 5.1 放行门定义

Wave 1 → Wave 2 的准入条件（全部满足才放行）：

| # | 条件 | 阈值 | 度量方式 |
|---|---|---|---|
| **G2-1** | 全池胜率 σ | **≤ 12pp** | Gate C 全量仿真 |
| **G2-2** | T1 vs T4 对位胜率差距 | **≤ 60%**（差距 ≤ 20pp） | Gate C 分层对位 |
| **G2-3** | 极值英雄（<25% / >75%） | **≤ 5%** 总池 | Gate C-5 |
| **G2-4** | 真实技能覆盖 | **≥ 80%** | 自动化盘点 |
| **G2-5** | Gate C-7~C-12 战斗节奏全套 | **PASS** | 自动化 |
| **G2-6** | IP 合规文件（ATTRIBUTION + 免责声明） | **100% 齐备** | 文件存在性检查 |
| **G2-7** | 公有领域 IP 候选池审批 | **用户已审批 ≥ 3 个候选 IP** | 人工流程 |

**放行逻辑**：

```
IF G2-1~G2-7 全部满足:
    → Wave 2 准入，开始新增公有领域 IP
ELSE IF G2-1~G2-5 全部满足但 G2-6/G2-7 未满足:
    → HOLD：补齐合规文件 + 候选池审批后放行
ELSE:
    → BLOCKED：σ 未收敛到安全线，新内容会等比放大失衡
```

## 6. 风险与缓解

### R-1 数据质量风险 — **高**

| 项 | 内容 |
|---|---|
| **描述** | 1078 条源技能需人工/半自动补齐。若沿用"复制模板改个名字"的思路，会批量产出 T4 级"伪真实"内容——名字真实但 effects 同质化，重演 T4 模板卡的 84.8% 败率问题 |
| **早期信号** | 新批次内 effects 类别熵 < 已有 T1 的 entropy；骰期望方差 < 3.0 |
| **缓解** | ① Gate A-2 强制非模板名 + Gate C-13 强制骰配额；② Phase 3 人工双关口审查；③ 每批次抽检 10% 人工评审"机制辨识度"；④ 用同 IP 已有源数据作风格基线防同质化 |
| **残余风险** | **中**——机制辨识度无法完全自动化判定 |

### R-2 IP 版权合规风险 — **高（当前仍有欠账）**

| 项 | 内容 |
|---|---|
| **描述** | Wave 1 新增的技能名来自商业 IP（LoL/Dota2/HoK 等），技能描述如与官方 wiki 高度相似即构成侵权。当前 E-4（ATTRIBUTION 文件）、E-7（免责声明）**仍未落地**（Gate D 报告未提及） |
| **早期信号** | 技能描述与 wiki 原文相似度 > 60%（可自动化检测） |
| **缓解** | ① **Wave 1 启动前必须先补 E-4 + E-7**（P0 阻塞项）；② Phase 2 映射时对官方描述做 D&D 5e 改写——不止改措辞，机制层面对齐也要变形（如 LOL 的"造成 80/120/160/200/240 (+0.8AP) 魔法伤害"改写为"1d10+INT 奥术伤害，L9 升至 2d10"）；③ smite 神话英雄优先走公有领域神话重述（"宙斯 → 雷神·宙斯，闪电箭"→ D&D 版"雷霆投掷，2d8+WIS 闪电伤害"） |
| **残余风险** | **中**——商业 IP 存量风险无法归零，但可显著降低 |

### R-3 σ 改善不达预期的回退策略 — **中**

| 项 | 内容 |
|---|---|
| **描述** | 如果 1-A 完成后 σ 下降 < 3pp（预期 25.8→18pp，最差情况 25.8→23pp），说明"增加真实技能"对 σ 的改善不如预期，可能需要重新审视根因 |
| **早期信号** | 1-A 完成后 C-2（σ）降幅 < 2pp |
| **诊断路径** | 1. 检查新增 T1 英雄的胜率分布——如果集中在 50-60% 区间（"平庸真技能"），说明 effects 设计过于保守；2. 检查 T4→T1 转化英雄的骰期望变化——如果前后差异 < 5，说明模板骰值本身已合理（根因在 effects/豁免，不在骰值）；3. 检查 effects 覆盖率——如果新增 T1 的 effects/saving_throw 覆盖率与 T4 模板无显著差异，说明 Phase 2 映射质量不足 |
| **回退策略** | ① 如果根因是 effects 质量：暂停后续批次，对 1-A 新增数据做 effects 增强补丁后回归；② 如果根因是模板骰值已合理：Wave 1 的策略从"追量"转为"追质"——少做几个 IP 但每个 effects 更精心设计；③ 如果 σ 完全不动：重新审视 GDD §1.9-D 的分析框架，可能存在未被建模的平衡因子 |
| **残余风险** | **低**——分批推进本身就是风险控制，最差情况只浪费 1-A 的采集工时 |

### R-4 smite 神话英雄同名冲突 — **低**

| 项 | 内容 |
|---|---|
| **描述** | smite 的英雄名直接使用神话神祇名（宙斯、波塞冬、阿努比斯等），这些名字在 Wave 2 公有领域 IP 中也会出现 |
| **缓解** | smite 卡已有 `source: "希腊"` 字段，Wave 1 写入的技能直接复用该字段；Wave 2 新增神话英雄时使用不同的 `card_id` 前缀（如 `smite:宙斯` vs `greek_myth:宙斯`），两个"宙斯"是不同游戏的不同诠释，不冲突 |
| **残余风险** | 低 |

### R-5 第一批的流程风险 — **中**

| 项 | 内容 |
|---|---|
| **描述** | 1-A（LoL +134）承担"流程校准"职责——如果 Phase 1/2/3 的链路在第一批就跑不通，后续批次无法推进 |
| **缓解** | ① 1-A 启动前先做"微型试点"：选 5 个 LoL 英雄（如 丽桑卓/凯特琳/卡兹克/内瑟斯/吉格斯）跑通全流程，验证工时估计；② Phase 1 爬取脚本先写好并通过只读验证；③ 第一批设定显式的"流程健康检查"——Phase 1 爬取成功率 ≥ 95%、Phase 2 平均 15 分钟/英雄、Phase 3 抽检通过率 ≥ 80% |
| **残余风险** | 低 |

## 附录 A — 源数据条目格式模板

新增的 `data/skills/<game_id>/<英雄名>.json` 必须遵循以下格式（每英雄一个文件，内容为 4 个技能 dict 的 list）：

```json
[
  {
      "name": "冰霜之环",
      "key": "Q",
      "type": "法术",
      "action": "动作",
      "range": "近战",
      "target": "范围",
      "damage": {
        "dice_count": 1,
        "dice_size": 8,
        "bonus_attr": "INT",
        "type": "冷冻"
      },
      "effects": [
        {
          "type": "slow",
          "desc": "移动速度减半",
          "duration": 2,
          "target": "敌方"
        }
      ],
      "saving_throw": {
        "attr": "CON",
        "dc_formula": "8+PROF+INT",
        "on_save": "半伤"
      },
      "cooldown": 0,
      "description": "释放冰霜之环，造成1d8+INT冷冻伤害。目标须通过CON豁免，失败则速度减半2回合，成功则伤害减半。"
    }
    // ... (3 more skills with cooldown=1,2,4)
]
```

**必须满足的契约**：
- `key` = `["Q","W","E","R"]`，对应 `cooldown` = `[0,1,2,4]`
- `damage.dice_count` > 0（至少 3/4 技能）
- `effects` 非空 ≥ 2/4 技能
- `saving_throw` 覆盖率 ≥ 2/4 技能
- 骰期望 `E` 落入 24–34，且符合 role 偏置
- `effect.type` 必须是英文小写，命中 `core/mechanics.py` 别名表
- `saving_throw.dc_formula` 使用 `8+PROF+<主属性>` 格式
