## 1. 摘要

9 个新公版 IP 的 **support（辅助）** 角色卡，在等级 ≥5 的 **辅助 vs 辅助** 对局中，双方 HP 被永久锁死在满血，任何一方都无法造成净伤害，对局跑满外部回合上限（脚本侧 `MAX_TURNS = 300`）仍无 winner。

根因分**两层**：新 IP 辅助卡的治疗/护盾效果**未配置显式数值**，触发引擎的「10% 最大生命值」兜底，产出远超双方伤害潜力的护盾量；同时 `BattleSimulator` **没有任何平局 / 超时判负机制**，只能靠某方 HP 归零结束，因此必然无限循环。

| 项 | 数值 |
|---|---|
| 老 IP support 镜像组 | 28 组 |
| **未终结** | **0 组** |

> 对照组阴性 → 问题定位在**本次新增的 9 个 IP 的辅助卡数据**，而非引擎的通用伤害结算。

### 3.3 已排除项：与本次技能改名**无关**

- **A/B 实验**：把 164 英雄技能 `name` 全部换回通用占位名，**同种子**重跑 592 场 → 结果指纹**完全一致**。
- **源码佐证**：`core/simulator.py` 中 `skill_name` 变量不参与任何结算路径；结算读取的是 `skill_desc` / `effects`。

**结论：技能改名不是本 Bug 的成因，改名工作无需回滚。**

### 3.4 QA 复核新增发现（本次立项时静态扫描 `data/`，比原始工单更精确）

统计 support 卡上 `治疗` / `护盾` 两类 effect 是否配置了显式数值（`value` 或 `value_formula`）：

| 分组 | support 卡数 | 护盾 effect | 治疗 effect | 显式配值 | **落入引擎兜底** |
|---|---|---|---|---|---|
| **9 个新 IP** | **35** | 108 | 76 | **0** | **184 / 184 = 100%** |
| 老 IP（全部） | 2721 | 3 | 29 | 26 | 6 / 32 = 19% |

**两点关键结论：**

1. 新 IP 辅助卡的治疗/护盾效果 **100% 未配显式数值**，全部落入引擎兜底公式。
2. 老 IP 辅助卡**几乎不挂治疗/护盾 effect**（2721 张卡仅 32 条），且挂了的大多配了显式值 —— 这解释了对照组为何 0 未终结。

### 3.5 数值链路推导（引擎兜底公式）

`core/simulator.py:159-172`：

```python
def _effect_value(self, eff, attrs, side):
    v = eff.get("value")
    ...
    if v is None:
        vf = eff.get("value_formula")
        ...
    if v is None or v == 0:
        v = int((self.max_hp1 if side == 1 else self.max_hp2) * 0.1)   # ← 兜底：最大生命值 10%
    return max(1, int(v))
```

- lv18 辅助 `max_hp ≈ 1110` → 兜底值 `int(1110 * 0.1) = 111`
- 女娲大招「真仙降临」`effects` = `[{治疗, duration:0, 自身}, {护盾, duration:2, 自身}]`，**两条都无 `value`**
- → 每次施放产出 **治疗 111 + 护盾 111**，与工单实测数字完全吻合
- 每张辅助卡平均约 3 条护盾 effect 分布在 4 个技能槽（含低 CD 技能），护盾**几乎每回合都被重新覆盖**

### 3.6 锁死机制

1. 护盾在扣血**之前**全额吸收伤害（`core/simulator.py:427-434`）
2. 双方技能伤害 ≤ 护盾池 → 净伤害 **0**，HP 永不下降
3. 治疗被 `min(max_hp, hp + v)` 钳制（`:484`, `:488`）→ 满血时治疗溢出，但**不影响锁死结论**
4. HP 永远 > 0 → 四处 `winner` 判定（`:215`, `:221`, `:236/242`, `:254/260`）永不触发
5. 引擎无回合上限 → 无限循环，直到外部脚本的 300 回合上限强行中断

## 5. 根因分析

### 5.1 数值层：新 IP 辅助卡配置问题（根因）

新 IP 辅助卡的大招每回合产出 **治疗 111 + 护盾 111**，而双方技能伤害在护盾全额吸收后降为 **0**，HP 被永久锁死在满血，任何一方都无法造成净伤害。老 IP 辅助数值未出现此锁死。

**QA 复核补充精确机理（`3.4` / `3.5`）：** 该 111 并非卡面手工填写的数值，而是因为新 IP 辅助卡的 `治疗` / `护盾` effect **完全没有 `value` / `value_formula` 字段**（184/184 条，100%），从而落入 `_effect_value` 的兜底分支 `int(max_hp * 0.1)`。

> **这对修复方案有实质影响：** 修复不是「把 111 调小」这么简单 —— 卡数据里根本没有「111」这个可改的数字。**必须给这些 effect 补上显式的 `value` / `value_formula`**，否则数值永远由引擎兜底接管，且会随等级线性膨胀（等级越高护盾越厚，锁死越严重）。

### 5.2 引擎层：通用兜底缺失

`core/simulator.py` 的 `BattleSimulator` **没有「平局 / 超时判负」机制**，对战只能靠某方 HP 归零才结束；当双方都无法造成净伤害时，会无限循环到外部回合上限（脚本侧设的 300）仍不终结。

**源码佐证：**

- `winner` 仅在 4 处 `hp <= 0` 判定中被赋值（`:215`, `:221`, `:236/242`, `:254/260`），**无任何回合数或平局分支**
- `execute_turn()` 内**不存在回合上限检查**
- `MAX_TURNS = 300` 只存在于**测试脚本侧**（`tools/_smoke_new_heroes.py:57`），**不是引擎保障** —— 生产调用方若不自设上限，将真正死循环

## 6. 转派（Assignment）

### 6.1 → `design-strategist`（数值层 · 修根因）

**任务：** 修正 9 个新公版 IP 共 **35 张** 辅助卡的数值配置，使治疗 / 护盾不超过对方伤害潜力，确保每回合净伤害 > 0。

**具体要求：**

1. 为全部 **184 条** `治疗` / `护盾` effect 补上显式 `value` 或 `value_formula`（推荐用骰子表达式如 `"2d8+WIS"`，与引擎 `roll_dice_expr` 对齐，可随属性成长而非随 max_hp 线性膨胀）。
2. 数值上限约束：**单回合护盾总量 < 对手单回合期望伤害**，保证 (support, support) 对局每回合净伤害 > 0。
3. 参考老 IP 辅助卡的显式配值区间（26 条 explicit 样本）做横向对齐，避免新老 IP 强度断层。
4. 复核护盾 `duration` 与技能 `cooldown` 的搭配，避免低 CD 技能造成护盾 100% 覆盖率。

**交付：** 更新后的卡 JSON + 数值变更说明。

### 6.2 → `engineering-lead`（引擎层 · 修兜底）

**任务：** 在 `core/simulator.py` 增加「超时判负 / 平局」兜底机制，避免任何对局无限循环。

**具体要求：**

1. 在 `BattleSimulator` 内置回合上限（如 `MAX_TURNS`，默认值建议 100–300，可构造参数覆盖），**不依赖调用方自觉设限**。
2. 达到上限时按当前 **HP 比例**（`hp / max_hp`）判胜；比例相等则判**平局**。
3. 扩展 `winner` 语义以承载平局（构造函数注释已预留 `0|1|2`，`0` 可表示平局），并同步更新 `is_over` 属性与所有消费 `winner` 的调用方。
4. 建议附加「僵局早停」：连续 N 回合双方 HP 均无变化即提前判定，避免空转 300 回合。
5. 为新机制补单元测试（构造双方净伤害为 0 的场景，断言必定终结且不超时）。

**交付：** 引擎改动 + 单测 + 对现有调用方的兼容性说明。

## 7. 建议修复方案

两段修复**互为补充，缺一不可**：

| 层 | 修什么 | 性质 | 若只做这一半会怎样 |
|---|---|---|---|
| **数值层** | 补显式治疗/护盾数值，保证净伤害 > 0 | **修根因** | 引擎虽不再卡死，但辅助镜像仍会大量走到超时判定，对局体验是「磨满上限」而非真实对抗 |
| **引擎层** | 增加超时判负 / 平局兜底 | **修兜底** | 本次 35 张卡修好了，但下次任何净伤害为 0 的数值组合仍会无限循环，问题会复发 |

**建议落地顺序：** 引擎层先行（立即消除死循环风险，让 CI 信号可信），数值层随后（消除根因）。两者合并后统一走 §8 验证。
